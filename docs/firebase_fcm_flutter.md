# Firebase FCM — Flutter Integration

## Overview

Firebase is used **exclusively** for Cloud Messaging (FCM push notifications).
The app does **not** use Firebase Auth, Firestore, or Realtime Database.

---

## Initialization Order

```
main()
  └─ WidgetsFlutterBinding.ensureInitialized()
  └─ Firebase.initializeApp(options: DefaultFirebaseOptions.currentPlatform)
  └─ runApp(ProviderScope(...))
        └─ ElmoApp
              └─ ref.watch(fcmAuthSyncProvider)   ← watches auth state
                    └─ on isAuthenticated == true
                          └─ FcmService.instance.initialize(...)
                                └─ requestPermission()
                                └─ getToken()
                                └─ POST /fcm/register-token
                                └─ listen onTokenRefresh
                                └─ listen onMessage (foreground)
                                └─ listen onMessageOpenedApp (background tap)
                                └─ getInitialMessage() (terminated tap)
```

**FCM is initialized only after a successful login**, never during the splash
or login screens, so the token is always associated with an authenticated session.

---

## Key Files

| File | Purpose |
|---|---|
| `lib/firebase_options.dart` | Auto-generated by `flutterfire configure`. Contains platform-specific Firebase config (no secrets to commit separately — the file uses public API keys). |
| `lib/main.dart` | Calls `Firebase.initializeApp` before `runApp`. |
| `lib/features/notifications/services/fcm_service.dart` | Singleton wrapper around `FirebaseMessaging`. Handles permission, token, refresh, and message routing. |
| `lib/features/notifications/services/fcm_sync_provider.dart` | Riverpod `Provider` that watches `authProvider` and calls `FcmService.initialize()` / `reset()` on auth changes. Also handles logout cleanup. |

## FCM Token Lifecycle

### 1. Obtain Token

```dart
// Inside FcmService.initialize()
final token = await FirebaseMessaging.instance.getToken();
await onTokenObtained(token); // → POST /fcm/register-token
```

### 2. Register with Backend

```
POST /fcm/register-token
Body: { "token": "<fcm_token>", "platform": "android", "appVersion": "x.y.z" }
Response: 200 OK
```

The token is stored in `app_fcm_tokens` on the Backend, linked to the
authenticated user session (via cookies / Basic Auth header).

### 3. Token Refresh

```dart
// Inside FcmService.initialize()
FirebaseMessaging.instance.onTokenRefresh.listen((newToken) {
  onTokenObtained(newToken); // re-registers with Backend
});
```

Token refresh happens automatically when Firebase rotates the token.
The app re-registers without any user interaction.

### 4. Token Removal on Logout

`FcmService.reset()` is called on logout (via `fcm_sync_provider`).
This cancels all FCM listeners and clears the initialized guard.

## Expected FCM Data Payload

The Backend must send a **data-only** push payload (not a notification payload)
for foreground handling to work correctly on Android.

```json
{
  "alertId":  "1201",
  "type":     "overspeed",
  "deviceId": "5",
  "severity": "warning",
  "screen":   "alert_details"
}
```

| Field | Type | Description |
|---|---|---|
| `alertId` | String | ID of the `app_alerts` record on the Backend |
| `type` | String | Alert type slug (e.g. `overspeed`, `geofenceExit`) |
| `deviceId` | String | Backend device/vehicle ID |
| `severity` | String | `info` \| `warning` \| `high` \| `critical` |
| `screen` | String | Hint for navigation (`alert_details`) |

### What the App Does with the Payload

```
FCM payload received
  └─ read alertId
  └─ deduplication check (recentAlertIds set)
  └─ if foreground:
        └─ refreshFromFcm(alertId)
              └─ GET /alerts/unread-count   → update badge
              └─ reload list if on screen
  └─ if tapped (background / terminated):
        └─ store alertId in pendingNotificationAlertIdProvider
        └─ FcmEventListener navigates to /alerts/:alertId
              └─ GET /alerts/:id
              └─ PATCH /alerts/:id/read
```

The app **does not create an alert object** from the FCM payload.
The `alertId` is used only to fetch the real record from the Backend.

## Message Handlers

### `onMessage` — Foreground

Called when a push arrives while the app is in the foreground.

```dart
FirebaseMessaging.onMessage.listen((message) {
  // message.data contains the payload above
  notificationsProvider.notifier.addFcmEvent(message.data);
});
```

**No UI notification is shown automatically** in foreground on Android unless
`FirebaseMessaging.instance.setForegroundNotificationPresentationOptions`
is configured. The current implementation refreshes the badge/list silently.

### `onMessageOpenedApp` — Background Tap

Called when the user taps a notification and the app comes from background.

```dart
FirebaseMessaging.onMessageOpenedApp.listen((message) {
  final alertId = message.data['alertId'];
  pendingNotificationAlertIdProvider.notifier.state = alertId;
});
```

### `getInitialMessage` — Terminated Tap

Called once during `FcmService.initialize()` to handle the case where
the user tapped a notification while the app was fully terminated.

```dart
final initial = await FirebaseMessaging.instance.getInitialMessage();
if (initial != null) {
  // treated same as onMessageOpenedApp
}
```

## Android Configuration Notes

- `AndroidManifest.xml`: ensure `RECEIVE_BOOT_COMPLETED` and notification
  channel permissions are present (added by `firebase_messaging` plugin).
- `android/app/google-services.json`: must match the correct Firebase project
  and the app's `applicationId`.
- Notification channel for high-priority alerts can be customized in
  `android/app/src/main/res/values/strings.xml` (optional).
